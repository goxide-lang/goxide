# 编译器、Go 工具复用、LSP 与自举

LSP 设计已确认，实施范围为 [MVP-5](../pre-mvp-plan.md#后续阶段mvp)。编译器已有 `parser.ParseFile → expand.Expand → resolve.ResolveExpanded → check.Check → lower.Lower` 管线；LSP 与共享分析快照实施中；缓存与布局的分项进度见状态表。当前支持度与测试入口统一见[能力状态表](../mvp-gap-audit.md)。本文集中维护设计、内部实施顺序和验收条件。

语言语义沿用[已确认决策](decisions.md)、[前端 AST](frontend-ast.md)、[enum 表示](enum-representation.md)及已接受 RFC。D19/D20 的风险 warning 和长期分析边界不变；LSP 不新增语言规则，也不重启尚未完成的 workspace、迁入、vendor 或构建脚本阶段。自举目标单独保留在文末。

## 1. 仓库与职责

编译器和 LSP 在 `goxide/` 同仓、同一个 `github.com/goxide-lang/goxide` Go module 中实现，不新建 LSP 仓库、Go module 或父目录 `go.work`。入口为 `goxide lsp`，通过标准输入输出提供 LSP；日志使用标准错误。

拟定文件归属如下，目录随对应阶段创建：

| 位置 | 职责 |
| --- | --- |
| `cmd/goxide/` | CLI 与 LSP 启动、参数及进程退出 |
| `internal/analysis/` | 共享分析输入、只读结果及源码语义查询 |
| `internal/lsp/` | 文档版本、请求调度、取消、诊断发布与编辑转换 |
| `internal/lsp/gopls/` | 原版 gopls 进程、overlay 同步、请求及结果关联 |
| 现有 `syntax/expand/resolve/check/lower` | 继续各自的语言阶段，迁出重复编排 |
| 现有 `compile/project/typecheck/procmacro` | 项目准备、Go 导入、宏编译与受限执行资源 |
| `editors/vscode/` | 首个编辑器扩展，独立打包，语言逻辑放在服务端 |

同仓允许前端、查询、源映射和 CLI 在一个主题提交中协调修改；分析接口保持内部 API。现有 Go parser/types/format 用于原生 Go、类型信息及生成输出，Goxide 语法继续使用现有 parser。原版 gopls 作为外部进程通过公开 LSP 协议接入，不依赖其 `internal` 包或私有嵌入 API。编译器新增实现使用 Go 标准库；现有依赖继续按 `go.mod` 固定，新增库另行决定。

## 2. 一套语言分析与资源生命周期

```text
源码与配置快照 → parse → configure/expand → resolve → check → Analysis
                                                           ├→ 源码查询
                                                           └→ lower → Go 与源映射
                                                                      ├→ Go 校验 / 构建
                                                                      └→ gopls overlay
```

CLI、LSP 和网站共用语言分析内核；网站沿用其现有导入器与宏宿主，不启动 gopls。宏登记、预解析、依赖发现及展开的固定点流程仍按现有语义执行，不另写一套编辑器近似实现。移出 `lower.CompilePackage`、`lower.CompileModules` 中重复的前端编排，`lower` 消费已分析结果并生成普通 Go。

共享接口按以下职责实现，名称为内部合同示意：

```text
compile.Prepare(ctx, request)             → Project
Project.Snapshot(ctx, overlays)           → Input
analysis.Analyze(ctx, Input)              → Analysis
compile.GenerateAndCheck(ctx, Analysis)   → Output
Project.Close()                          → 释放资源
```

- `Project` 保存选定的项目图、配置、Go importer 和宏资源；准备、读取与分析同产物发布分开。现有只在回调期间有效的 `PreparedSources` 不能直接成为长期快照。
- `Input` 固定源码字节、文档版本、输入集合、目标与有效配置；包括未保存的 `.gox` 和 `.go`。依赖、feature、tags、环境读取、Go 工具链和运行时支持库选择与 CLI 一致。
- `Analysis` 发布原始/展开语法、解析绑定、类型、成员及 impl 选择、结构化诊断与各区域的可用范围。普通源码错误保留部分结果；取消、I/O 和工具进程故障作为执行错误处理。
- `Output` 包含生成 Go、来源映射和完整校验诊断。编辑用投影共用 lowering，并标记可用范围；它只用于查询，不作为可执行构建产物发布。
- 任务持有其快照及依赖资源直至结束；关闭项目先取消并等待任务释放，再关闭 importer、宏宿主与临时目录。LSP 不长期持有 CLI 的项目写锁或整个 target 的发布租约。

原始 AST 发布后不可变，配置筛选和宏展开构造工作树；未变化节点可共享，不为只读约定无条件深复制整棵树。`NodeID`、`SyntaxCtx`、符号和类型对象在所属文件版本及分析上下文中解释；依赖与配置未失效的不可变 AST、包结果可跨代共享，不能把过期结果或不同 importer 身份混入当前快照，也不能把编号当持久身份。新节点保存来源关系，查询使用现有 resolve/check 事实，不建立第二套绑定或类型系统。

后端不得修改已发布的 `check.Info`；后端临时选择、Go 类型及验证树使用私有状态。所有泛型定义和条件分支的定义点检查、最终生成 Go 的类型检查继续执行，不能因没有调用某个定义而省略。快速源码诊断和完整后端诊断绑定同一代，完整结果到达后合并。

## 3. parser 与源码模型的重构范围

保留现有 lexer/parser/AST，先完善恢复和源码归属：

1. 缺失标识符、类型、表达式和分隔符使用明确的缺失/错误节点；真实 `_` 与恢复占位符分开。恢复不得消耗闭括号、文件末尾或下一个声明的同步边界。
2. 函数体局部错误保留函数名称、泛型参数、参数和返回类型。停止因局部错误无条件把整个父声明替换成 `BadItem`；已识别的正常兄弟声明保留。
3. 原始树保留分组 `use`、书写形式、注释、指令与 token；展平、配置删除和宏改写移至后续工作树。来源从原始节点持续关联到展开节点和 Go 节点。
4. 源码 span 使用字节半开区间；统一位置模块按协商编码转换 LSP 位置，覆盖默认 UTF-16、非 ASCII、代理对、CRLF 和文件末尾空行。
5. 原生 `.go` 使用 Go parser 并保留可恢复的树。声明投影若需删除函数体，只修改工作树，保留原始 Go 文本和 AST 供查询及映射。

恢复验收包含 `x.`、`Foo::`、未闭合调用/类型参数/块、缺失宏参数、文件末尾截断，以及错误之后的正常函数。验收同时检查诊断位置、保留的声明和可查询区域；不能只断言 parser 不 panic。

完整增量 parser 由性能数据决定。先使用不可变文件结果和包级失效，避免同时重写语法和引入复杂增量树。

## 4. 部分分析与源码查询

共享查询直接使用当前快照的作用域、定义/引用、类型、成员、关联类型和已选 impl。Go 与 Goxide 的类型身份在本轮 importer 中保持一致，不能用两个独立 importer 的对象拼接同一语义图。原生方法导航到 Go 定义，有体 impl 导航到业务体，生成 carrier/wrapper 关联其源码来源。

| 当前输入 | 查询与投影行为 |
| --- | --- |
| 声明与函数体完整 | 正常分析、完整 lowering，提供当前语义结果 |
| 签名可靠、函数体不完整 | 保留签名和已知作用域；编辑投影可使用占位体，原始源码错误继续发布 |
| 签名或宏生成的声明集合未知 | 相关事实标记不可用；不沿用旧声明伪造当前类型 |
| impl 冲突等使协议选择不可靠 | 保留诊断，阻断依赖该选择的查询和 lowering |
| 独立正常声明/包 | 在其依赖信息可靠时继续分析和查询 |

声明投影只能从共享分析中已确认的事实生成，不用正则或另一个宽松 parser 猜签名。占位体通过 Go 检查不能清除 Goxide 错误。受未知依赖影响的 Go 级连锁错误由可用范围过滤，保留有意义的根因。

首版提供诊断、定义导航、悬停、基础补全和文档符号。宏生成成员保留定义/调用来源；展开预览只读。请求当前编辑无法支持的语义时返回明确不可用或等待对应分析，不能把上一代结果标为当前结果。

## 5. 项目输入、原生 Go 与生成物

项目准备复用现有 `internal/project` 和 `internal/compile` 的选择规则，不在 LSP 内另建依赖图或包管理器。原生 Go module 沿用作者目录和 Go 模块环境；TOML 项目由现有 loader 准备稳定的私有 Go 视图。首版不增加 `GOPACKAGESDRIVER`，不把所有原生 Go 项目复制到镜像目录。

依赖更新、源文件新增/删除、配置变化统一进入会话变更队列。原生 Go 代码、测试包变体、构建约束、相对 replace、资源与 `go:embed`、项目已有的 cgo 能力按当前入口规则处理；私有视图需要保留这些行为。嵌套 module、受管产物和依赖根沿用项目边界。

`gen` 项目统一生成物识别与所有权规则：

- 在受管理的源码范围内，仅把具有 Goxide 自身生成标记的 `_gox.go` 作为本工具输出；包括对应 `.gox` 已删除的孤儿输出。
- 手写同后缀文件、其他生成器输出及 Go-only 发布依赖中的正常 `.go` 仍作为 Go 输入。
- 源码分析排除本工具磁盘输出；Go 投影由当前 `.gox` 生成结果与当前手写 `.go` 组成，不能同时导入旧生成声明。
- 编辑会话不修改作者源码或磁盘生成文件。生成预览与诊断位置回到来源；正式 `gen` 的写入仍由 CLI 执行。

## 6. 原版 gopls 的投影与版本协调

### 6.1 进程和文件生命周期

使用标准 `file://` URI 和 LSP overlay；新增 Go 文件及尚无磁盘目录的包可通过 `didOpen` 提供。gopls 的普通 Go 能力与 `.gox` 服务由同一个 Goxide 会话协调，编辑器扩展避免在同一受管项目另开不共享投影的 Go 客户端。

虚拟生成文件使用稳定 URI，不按源码 hash 或编辑次数改路径。新增/修改使用 `didOpen`/`didChange`；无磁盘对应文件的虚拟文件可在删除时 `didClose`。有磁盘旧输出时，关闭 overlay 会恢复磁盘内容，应保持如下屏蔽 overlay，包名沿用该文件的合法包名：

```go
//go:build ignore && !ignore

package p
```

恒假构建条件使旧声明退出 Go 包；删除最后一个源文件时，该包也应退出导入图。磁盘旧文件真正删除后释放屏蔽；若其已成为普通 Go 输入，则按新的分类和内容同步。 原版 gopls v0.24.0 在包的最后文件解除屏蔽时不会自动重载消费方的缺失导入；协调器在整代 overlay 更新后，用同一条 `workspace/didChangeWorkspaceFolders` 移除并重新加入原工作区，保留 overlay 并刷新 view。该额外工作仅用于解除屏蔽的拓扑变化，普通编辑仍只同步变化文件。启动、重启、重命名及配置切换均重建完整的当前文件/屏蔽集合，不能只处理本次编辑的文件。

### 6.2 整代更新与请求

每次已接收的输入变化产生内存中的分析代号；它是会话序号，不是源码内容摘要或持久缓存目录。

1. 固定本轮输入，在内存中准备本代 Analysis、Go 投影、删除/屏蔽集合、源映射和可用范围；部分分析按第 4 节保留可靠区域。
2. 在一个串行写入队列内连续发送本代全部文件更新，中间不插入语义查询；文件版本在同一 gopls 进程内递增。
3. 随后发送查询，并记录请求对应的分析代号、源码/投影版本和映射。同代诊断请求连续入队，不在其间插入下一代修改。
4. 新输入使旧任务失效并尽早取消。响应只按请求时的映射解释；代号过期则丢弃，不能用最新映射修补旧结果。
5. 进程退出或投影更新失败时停止该进程的结果发布，重新准备完整当前状态后恢复查询。

gopls 按输入顺序处理消息，pull diagnostic 在异步计算前取得快照；逐条 `didChange` 仍可能形成中间态。[消息顺序](https://github.com/golang/tools/blob/24a65270771e/internal/jsonrpc2/handler.go#L80-L123)、[诊断快照](https://github.com/golang/tools/blob/gopls/v0.24.0/gopls/internal/server/diagnostics.go#L36-L76)。不能把普通请求返回、stdio flush 或 progress end 当成多文件原子提交。

同代保证针对协调器已接收的输入。关闭 gopls 自行监听，客户端文件事件统一排序；已选择的可变源码按快照同步。外部进程并发修改磁盘、配置或本地依赖时，使受影响代失效并重新准备；稳定私有目录本身也不是整个文件系统的原子快照。

### 6.3 诊断来源与协议边界

Goxide 负责源码诊断、完整编译校验及项目配置诊断；gopls 补充 Go 文件的语言服务与分析诊断。相同诊断按来源和范围合并，删除文件时主动清理诊断。

原始 `publishDiagnostics` 不直接转发：未改动文件的 version 可以相同，而其依赖包已处于不同中间态。用户可见的 gopls 诊断采用按代发起的 pull 请求，由 Goxide 重新组织发布。

对接起点为原版 gopls v0.24.0 的公开协议行为。其 pull diagnostics 为实验能力，仅支持 Go 文件，缺少 workspace diagnostics、resultId、相关文档及完整多视图/模块文件支持；响应结构也需由客户端整理。能力检查、错误处理和实际响应形状纳入协议测试，升级 gopls 时重跑契约测试。Go 模块文件诊断不能依赖这一实验入口，使用共享项目加载/校验结果。

首版按选定构建配置组织会话；其他目标的结果不混入当前快照。缺少 gopls 或启动失败时保留 Goxide 自身已可靠的源码能力，报告 Go 服务不可用；不静默安装或切换到另一套语义实现。

## 7. 源映射、诊断与编辑

来源链包含原始文件版本与字节 span、展开节点、宏定义/调用栈、生成 Go AST 和格式化后的 Go 范围。泛型定义验证等临时 Go 树同样有来源。格式化变化后仍按实际输出定位，不能使用行号差或最近节点猜测。

映射明确区分三种结果：精确可编辑源码、具有宏来源但不能直接反向编辑的派生代码、纯合成代码。定义/悬停按来源返回源码位置；宏模板错误给定义点及调用点，捕获输入错误指向调用者。纯合成代码保留生成位置或只读预览，不能伪造可编辑源码 span。

编辑操作在服务端完整验证：

- 检查请求所属代号和全部目标文档版本，使用版本化编辑；过期则拒绝或在新快照重算。
- 精确一一映射可以直接转换。`pub foo → Foo`、宏复制、carrier/wrapper 等必须按源码符号重新规划，去重并检查名称/作用域冲突，不能只替换显示文本。
- 无法解释、范围重叠冲突、缺少来源或只完成一部分的 WorkspaceEdit 整组拒绝。
- completion 的附加编辑、code action 及命令产生的后续编辑使用同一规则；gopls 命令不得绕过源文件/产物边界直接修改项目。
- 可靠重命名及代码操作阶段对候选源码重新分析，并验证重新生成后的引用关系。后端生成符号不是用户重命名接口。

## 8. 过程宏与第 2 级缓存

声明宏按既有规则展开；过程宏解析、登记、编译并执行，二者展开结果参加正常的 resolve/check。过程宏依赖已知后可在后台预编译，用户查询复用已准备结果。

| 复用级别 | 合同 |
| --- | --- |
| 1：依赖 | LSP 与 CLI 共享已下载、按所选版本校验的依赖 |
| 2：宏编译 | 共享 Go 编译缓存和宏编译产物的稳定槽位；CLI 依据自己的当前输入确认构建并执行宏 |
| 3：展开语义结果 | 不在 LSP 与 CLI 间共享展开 AST、卫生绑定、类型或调用点结果 |

实现目标固定为第 2 级。当前输入先经共享前端准备，再调用 Go 构建确认新鲜度，复用 Go 自身缓存；不因磁盘存在某个 WASM 就判定命中。它可以复用已编译工作，仍可能启动 Go 命令并重新链接。LSP 未保存输入与 CLI 磁盘输入使用隔离工作槽及原子发布，不能覆盖对方仍在使用的产物。

失效规则：调用参数变化重做受影响展开；宏源码、传递本地依赖、选中版本/replace、feature、有效配置、工具链或 SDK 变化时重建受影响宏，再分析调用方。远端出现尚未选中的新版本不自动升级项目依赖。取消或失败结果不进入成功缓存。

LSP 内部缓存按输入版本和依赖关系失效；调用点、fresh bindings 和来源始终属于当前快照。长期复用的 WASI 编译资源与每轮执行实例、预算、截止时间、取消状态分离，单次失败不污染下一次执行。

## 9. 稳定产物路径与 OS-ARCH

L4 调整 `build/run` 的配置身份和 `units/bin` 布局：删除 `stagedContent` 等整份源码内容进入 `UnitSpec.Config` 的路径分裂，不新增编译器自维护的全源码 hash 索引或内容寻址目录。Go/gopls 自身缓存、依赖完整性校验及已有产物覆盖保护按各自规则使用。

目标布局为：

```text
target/
  units/<target>/<kind>/<name>/<config>/
  bin/<target>/<kind>/<name>/<config>/
```

`target` 为规范化 GOOS-GOARCH，目录中只保留一次。宿主信息仍记录于元数据；确实影响构建的宿主差异进入配置身份，不保留重复的 Host/Target 路径层。配置身份包含真实构建选择，不因普通源码内容编辑变化。

同配置生成视图、宏槽位和最终输出路径稳定复用；只更新变化字节，保留相同文件的 mtime，移除本工具拥有的失效文件。进行中的工作目录数量受并发限制，任务完成即清理；不能每次编辑永久新增目录。沿用覆盖保护、短期发布互斥与失败时保留上一份有效二进制的行为。

[现有 target 布局](target-layout.md)描述当前实现，L4 按本节替换 `units/bin` 路径后同步该文档；不为旧布局增加迁移或兼容分支。本阶段不顺带改构建脚本缓存协议。

## 10. LSP 与 build/run 的性能合同

两条路径分别建基线、测量和验收，不能用交互改善抵消构建退化，也不能用 Go 编译总时间掩盖前端重复工作。以下预算是实施目标，尚无完整 LSP 的性能测量。

设计本身有以下潜在成本，需要在实现中控制并测量：

| 路径 | 可能的负面影响 | 控制方式 |
| --- | --- | --- |
| LSP | Goxide 和 gopls 各持有语法/类型数据，增加 CPU 与内存 | 按需查询、差量投影、有界缓存；同时测两个进程，不能假定跨进程共享类型缓存 |
| LSP | 原版 gopls 后台诊断与主动 pull 重复消耗计算 | 核对支持的诊断调度选项并减少无用分析；丢弃 push 只隔离结果，不等于省掉计算 |
| LSP | 整代更新等待、源码映射与进程通信增加延迟 | 快速源码查询独立服务，投影更新只发差量，分项测量生成/排队/IPC/查询耗时 |
| CLI | 快照、恢复树和精确来源增加分配，接口拆分引入重复工作 | 按消费者保留数据、共享不可变节点或转移所有权；逐阶段检查调用次数、分配和峰值内存 |
| CLI | 宏新鲜度检查仍启动 Go 命令，缓存命中仍可能链接 | 复用 Go 缓存与稳定工作槽，实测编译/链接次数，不以“命中”推断零构建成本 |
| 并行使用 | LSP 后台分析/宏编译与 CLI 争抢 CPU、I/O 或发布锁 | 限制后台并发，取消过期工作，短期发布互斥；单独验收同时使用时的等待与耗时 |

### 10.1 LSP 交互路径

- 热查询读取已发布索引和分析事实，不触发全包解析、宏编译、Go 命令或全图类型检查。
- 普通编辑先更新该文件的语法结果，再按依赖关系重算受影响区域；未变依赖结果可复用。每个项目配置保留最新待分析状态，取消过期分析，有界后台并发防止逐按键任务积压。
- 宏编译只由相关宏输入/配置变化触发，调用参数变化复用已编译宏；保存未变内容不应重启同一轮分析。
- Go 投影按变化文件发送，稳定 URI 保留 gopls 缓存。只拉取需要展示及受依赖变化影响的诊断；不能每次按键遍历所有文件拉取。
- 快速源码诊断、完整定义/Go 校验和 gopls 分析按职责调度，避免重复执行等价检查；完整校验在后台完成，错误不能因快速路径而永久遗漏。
- 只保留正在使用及必要缓存中的快照，限制宏编译缓存和展开产物内存；关闭项目后释放进程与资源。

初始交互预算：在 L0 固定的代表性项目、机器和热缓存条件下，热悬停/定义/补全 p95 不超过 100 ms，普通函数体编辑后的源码诊断 p95 不超过 1 s。冷启动、首次宏编译、宏依赖变化和完整 Go 校验单独测量，不混入热查询数字；这些任务也不能阻塞文档接收与请求取消。

### 10.2 CLI 构建路径

- 普通 build/run/test/gen 不启动 gopls、监听器或 LSP 索引，不保留会话历史。共享代码按需要产出结果，不要求 CLI 建立编辑器专用数据。
- 一次输入只分析一次，生成和检查复用该 Analysis；拆分接口不能导致 Prepare、Analyze、Generate 各自重新解析/展开/检查。
- 不为只读快照无条件复制所有源码或 AST；CLI 无并发读者且不需保留原始树时可转移所有权，已发布数据仍保持只读。源映射按消费者需要构造，CLI 保留准确诊断所需来源，不额外生成无人使用的完整编辑索引或 sidecar。
- 复用当前生成/最终 Go 校验流程，保留泛型定义检查；不能通过省略检查制造性能改善。缓存共享不增加每次构建的全源码 hash 扫描。
- 同配置稳定路径、差量写入和共享 Go 缓存维持重复构建收益；LSP 后台工作不长期占用 CLI 发布锁，二者并行时测量 CPU、内存及等待时间。

验收分别记录前端解析/展开/检查、lower/格式化/映射、宏编译、Go 校验/编译/链接和总耗时。已有模块冷构建、无改动热构建、单函数修改、宏参数修改、宏依赖修改及 build 后 run 分别对比；同时记录峰值 RSS、文件写入量、目录数量和 Go 子进程次数。

### 10.3 测量与回归判断

L0 固定项目规模、工具链、机器、配置、冷热缓存定义、样本数和噪声范围。使用交替运行的基线/候选测量，报告中位数、p95 和内存；冷依赖下载与纯计算分开。LSP 测量从收到编辑/请求到结果可见的耗时，并覆盖持续快速编辑和 LSP/CLI 同时工作。

LSP 场景分别包含冷启动到首次查询/完整诊断、热查询、函数体编辑、公开声明/配置编辑、宏参数编辑和宏/传递依赖编辑。源诊断与完整 Go 诊断分别计时；L0 固定各类输入停止后到完整同代诊断的预算和超时。仅在泛型定义验证或最终 Go 检查中出现的错误，也必须在该预算内发布，不能以快速语法诊断掩盖完整检查长期未完成。连续至少 1,000 次可复现编辑后，任务队列应收敛，已结束代可释放，同配置源码编辑不增加持久目录数量。

超出基线波动范围的稳定 CLI 回归须定位并解决；LSP 还须达到上述交互预算。不能放宽阈值、缩小样例或丢弃失败/取消样本掩盖退化。测试及基准入口随实现交付，运行日志不追加到设计文档。

## 11. 实施阶段与验收

L0–L7 是 MVP-5 内部实施顺序和验收门槛，MVP-5 在完整闭环验收后交付。进度只记录在能力状态表；实现按下列阶段推进。

| 阶段 | 主要归属与交付 | 退出条件 |
| --- | --- | --- |
| L0：合同与基线 | 固定输入/分析/来源/投影合同；编译器、gopls 协议和性能基线 | 四边界成为可重复的契约用例；确定性能样例与预算；原有 build/run/test 行为有对照 |
| L1：parser 与来源 | `internal/syntax`，恢复节点、原始树、位置转换 | 错误输入保留正常声明；Unicode/CRLF/末尾位置通过；解析及内存回归检查通过 |
| L2：共享分析 | `analysis` 与现有 compile/lower/resolve/check，收敛重复前端流程 | CLI 和网站接入同一语言分析；生成模块真实 build/run/test；重复生成字节一致；无重复分析回归 |
| L3：后端与映射 | `lower/typecheck`，隔离后端状态、编辑投影、完整诊断来源 | 正常及不完整输入有可靠来源；临时验证代码可定位；映射开销与 CLI 所需产出分别验证 |
| L4：会话、宏与布局 | compile/project/procmacro 与 LSP 会话，有界缓存、失效、取消、稳定目录 | 第 2 级复用及依赖刷新通过；LSP/CLI 不串输入；无源码 hash 目录增长；目标平台一层；构建性能无稳定回归 |
| L5：gopls 接入 | `internal/lsp/gopls`，文件生命周期、整代更新、结果关联 | 四边界用真实 Goxide 生成链路验收；覆盖新增/删除包、重命名、配置切换、过期结果和进程重启 |
| L6：首版服务 | `cmd/goxide`、`internal/lsp`、编辑器扩展，首版五项能力 | 单文件、目录、TOML、多包及 Go 混写按支持范围工作；未保存输入和过程宏可编辑；达到热交互预算 |
| L7：集成收敛 | 当前模块的回归、并发、资源及性能检查 | 共享状态 race 检查通过；真实项目端到端通过；无过期响应、用户源码写入、任务/进程泄漏或无界缓存增长 |

四个关键边界的行为验收必须覆盖：

| 边界 | 必须可证伪的用例 |
| --- | --- |
| 删除与所有权 | 有磁盘旧生成物、纯内存新文件、孤儿输出、删除包的最后文件、重命名及重启；旧声明不复活；手写同后缀和 Go-only 依赖不被屏蔽 |
| 多文件一致性 | A/B 共同改变类型，未改 C 的诊断随依赖变化；刻意延迟两次更新并制造乱序响应；对外无中间态、旧代诊断或旧映射编辑；配置/依赖变化使旧代失效 |
| 映射与编辑 | 跨文件/包导航，Unicode/CRLF，宏定义/捕获/嵌套展开，格式化偏移，泛型验证树；合成/冲突/过期编辑整组拒绝；可用编辑重新分析及生成构建通过 |
| 不完整输入 | 选择器/路径/宏/括号截断保留正常声明；签名变更不显示旧签名；未知声明和 impl 冲突阻断依赖事实；占位投影不能掩盖源码错误 |

其余集成验收覆盖：CLI/LSP 相同输入配置的符号与诊断一致；宏卫生和字段参与行为；原生 `.go` 未保存变化；测试包、tags、replace、资源及当前支持的 cgo；连续快速编辑、取消、进程失败及项目关闭；宏缓存冷热等价；目录数量有界；性能按第 10 节分别验收。

实现阶段在 `goxide/` 使用 `go.mod` 指定的本地 Go，运行仓库规定的检查：

```sh
export GOTOOLCHAIN=local GOWORK=off
go build ./...
go test -count=1 ./internal/... ./tests/...
go vet ./internal/... ./tests/...
gofmt -l internal cmd
python3 -B scripts/check_design.py --docs-only
```

共享分析、会话、宏宿主和 gopls 生命周期增加相应 race 检查。端到端测试必须生成 Go 并真实 build/run，涉及项目测试时真实 test；同输入两次生成字节一致。纯文档阶段只运行文档检查；网站行为变更另按网站既有入口验收。

## 12. 后续演进与自举

首版之后依次完善跨包引用/高亮/实现定位/签名帮助、可靠重命名、语义代码操作、格式化与重构。第 7 节的来源与编辑合同从基础设施阶段落实，能力完成验收后再对编辑器声明支持。

性能演进顺序为文件结果复用、受影响包重算、区分声明变化与函数体变化、按需函数体检查；完整增量 parser 只在实测为瓶颈后推进。任何缓存命中都必须保持绑定、权限、宏来源和完整诊断一致。

Goxide 自举仍是后续目标，不改变普通 Go 输出和 Go 工具链主线。Go 种子编译器已存在；迁移子集、逐模块次序及发布恢复策略另行确定。逐模块迁移需让同一回归集通过，自编译验证需固定输入与工具链并比较生成结果和程序行为；本轮 LSP 设计不启动自举实施。

Rust/LLVM 到 Plan 9 汇编等独立后端研究不在本阶段。Go 调用约定、栈与 GC 协调需单独验证，不能以替换后端为由改变已选 impl 或外部能力。参见 [Go 汇编与运行时协调](https://go.dev/doc/asm#runtime)及 [Go 内部 ABI](https://github.com/golang/go/blob/master/src/cmd/compile/abi-internal.md)。
