# 编译器、Go 工具复用、LSP 与自举

D21 优先级下继续复用 Go 后端；R24/RFC0019 已确认统一 wrapper。旧[trait 双路径研究](../rfcs/research/0004-trait-lowering-paths.md)保留为历史对照，不能以优化为由改变选中 impl、动态身份或外部能力。

交付边界（D20）：本文涉及的别名/借用风险 warning 是未来独立长期分析，不属于 MVP 验收；当前语言语法、类型、明确操作与真实 Go 行为照常设计。不得为未实现分析器强制复杂效果注解。

状态：本文记录此前讨论中的架构方向和未定实现选择。**已确认**的是生成普通 Go、转译前检查、Go 生态互操作与 goxide 源码级 LSP；未来使用 goxide 自举是用户提出的目标。**暂定**采用 Go 编写启动实现、共享 goxide 前端及分阶段自举。解析器来源、查询实现、CLI、输出目录和发布协议均未定；当前没有编译器或 LSP 实现。

三态定义与跨专题决策以[决策登记](decisions.md)为准。

诊断默认遵循 D19：真实语法/类型错误阻断；有具体别名、逃逸、并发或锁协议风险给 warning；未知效果不作普通 Go 调用的准入限制。严格模式未批准。

逐特性输入输出及验收约束见 [RFC 清单](../rfcs/README.md)；本篇负责架构，不替代具体 lowering 契约。

## 1. Go 源码是主线输出

goxide 先检查自身语义，再生成标准 Go 源码，由 Go 工具链负责机器码、运行时与链接。最低目标语言及工具链版本为 Go 1.27，这来自已确认的泛型锁方法需求；生成模块与支持库的语言版本也必须相应设置。

包加载采用同一 Go 模块携带 `.go`、`.d.gox` 与可选 `.gox`：Go 只编译 `.go`，goxide 额外选择声明或源码，不重复编译同一生成实现。来源识别协议尚待实现；见 [RFC 0001](../rfcs/0001-package-loading.md)。

前端必须保留 Go 不认识的语义：显式 impl、trait 视图选择、关联类型、枚举合法性与穷尽性、卫生来源、引用权限、unsafe 效果及公开边界。不能先把它们擦成 Go 类型，再以 Go 能编译为充分验证。

函数和方法声明保留来源区别：直接书写的原生 Go 声明按 Go 语义处理，impl 成员按 goxide 规则降低。前端为 impl 的 Self 记录目标类型，为实例成员的 self 记录接收者绑定及权限；关联函数没有隐式 self。后端按绑定生成类型、接收者访问和已解析调用，不对原生声明或全文件执行 Self/self 文本替换。具体对照见 [RFC 0020](../rfcs/0020-associated-functions.md)。

需要普通 Go 支持类型时生成或调用普通支持库；trait 在 impl 包生成 wrapper、marker、固定适配函数及便利 helper，详见[当前适配方案](go-interop.md)。构建驱动确定 Go 模块图、平台 / tags、声明集合和生成集合；无需为 trait 改写原生依赖或 GOROOT。具体驱动接口仍是实现草案。

## 2. 启动语言的暂定选择

此前比较 Go 与 Rust 实现前端后，当前建议采用 **Go 编写种子编译器与 LSP**。理由是能直接使用 Go 包加载与类型库，且以后可逐模块迁移为 goxide；这是一项暂定实现选择，不把“用户提出未来自举”扩大成“所有实现细节已经确认”。

Rust 也可以实现前端，但会带来与 Go 类型加载侧的进程 / 数据适配，以及后续迁移语言的额外工作。前端用哪门语言与最终输出 Go 源码是不同决策；采用 Go 启动也不要求 goxide 的所有内部结构等同于 Go AST。

## 3. 可以复用哪些 Go 工具

| Go 工具 | 暂定复用范围 | goxide 仍需承担的工作 |
| --- | --- | --- |
| `go/token`、`go/scanner` | Go 位置和词法设施，或其实现思路 | 新 token、宏 token tree、来源及分号规则 |
| `go/parser`、`go/ast` | 解析原生 Go；构造 / 检查生成 Go AST | goxide 新语法及自己的语法树 |
| `go/types` | 原生 Go 类型、方法集、泛型实例和类型信息 | 显式 impl、枚举、权限、宏卫生及其他源级规则 |
| `go/format` | 格式化已生成的 Go 源码 / AST | goxide 源码格式化；保留生成前后的映射 |
| `golang.org/x/tools/go/packages` | 按构建配置加载 Go 包、依赖、语法与类型 | `.gox` 发现、声明元数据与普通 Go 生成产物 |
| gopls | 架构参考；按需辅助生成 Go 的语言服务 | 面向 goxide 原始源码的完整语言服务 |

这些库服务于 Go，并非已经实现扩展语言的前端。[Go parser](https://pkg.go.dev/go/parser)、[Go scanner](https://pkg.go.dev/go/scanner)、[Go types](https://pkg.go.dev/go/types)、[Go format](https://pkg.go.dev/go/format)、[Go packages](https://pkg.go.dev/golang.org/x/tools/go/packages)

`go/parser` 没有注册 enum / match / 宏语法的插件入口，`go/ast` 也不直接承载这些新节点。若语法保持接近 Go，可改造 Go 解析器源码并维护 goxide AST；也可以独立实现解析器。**两条实现路径尚未选定**，不能写成已经决定 fork 整个 Go 编译器。原生 Go 文件仍可走普通 Go parser。

`go/types` 在降低后的接口上允许 nil，并不会替 goxide 做 Result 的严格边界检查。其类型信息可复用，goxide 自己的事实必须同时保存；如何组织复用检查与独立检查的精确顺序，随前端原型验证。

gopls 的官方设计说明明确指出，扩展内部功能需要修改 gopls，并没有通用语言插件入口。因此当前方案不以“给 gopls 装一个 goxide 插件”作为架构前提，也不承诺仅增加 source map 就拥有完整 goxide IDE 体验。[gopls 设计说明](https://go.dev/gopls/design/design)

## 4. 暂定的共享前端结构

```text
goxide 源文件 + 声明依赖 + 实际 Go 包信息
                    |
         goxide token / AST 与来源信息
                    |
       展开、绑定、类型与转译前语义检查
                    |
          goxide 语义 IR 与查询结果
               /                 \
     Go AST / Go 源码          goxide LSP
               |
      生成包实现与声明元数据
               |
           Go 工具链
```

这一分层是暂定架构，不冻结 AST / IR 类型或包名。AST 保存源语法与来源；进入降低的 IR 应明确表示已选 impl、必要转换、合法 enum、控制流和权限。后端不能通过生成失败后添加 wrapper 或改类型来反推原程序意图。

宏的绑定与展开存在阶段关系，流程图不表示先完成全部名字解析才展开。具体草案见[宏专题](macros.md)；无论最终阶段怎样划分，编译命令与 LSP 应共享同一事实和诊断逻辑，不能各写一套近似规则。

公开的 syntax / quote / syn 协议与内部已解析 IR 分开。普通工具可以构造语法数据，但不能靠伪造 SymbolID、span 或缓存字段建立可信语义；详见[语法工具](syntax-tooling.md)。

## 5. LSP 与源码映射

提供 goxide LSP 是已确认目标；以下交付顺序和内部方法为暂定方案：

1. 先提供 goxide 源码诊断、符号导航、悬停和基础补全，保留不完整输入下的错误恢复。
2. 加入显式 impl 与关联类型查询、enum 缺失分支、原生 Go 方法导航和声明来源。
3. 加入宏展开来源、只读展开预览、卫生符号与重命名；最终补齐跨包引用和增量体验。

源位置应能关联原始 goxide、宏定义 / 调用与生成 Go；展开可能是一对多关系，不宜仅保存“生成行号减常量”。名字解析身份与源码 span 分别保存，重命名不得按同名文本批量替换。Go 后端诊断应尽量回映射到可修改的 goxide 源位置，必要时展示生成位置作为辅助信息。

LSP 与构建必须选择相同的 Go 版本、构建条件、模块图、declare / impl 集合及宏依赖。未保存编辑、增量失效、取消请求、跨包索引和错误恢复的具体协议尚未设计；复用 Go 类型库不会自动完成这些工作。

## 6. 自举路线草案

自举目标不要求替换 Go 的机器码后端，也不要求停止使用 `go/types` 等 Go 包。暂定通过以下阶段证明 goxide 能编译自己的实现：

| 阶段 | 输入与产物 | 完成条件 |
| --- | --- | --- |
| C0：Go 种子 | Go 编写的 goxide 编译器；实现可用于编写前端的最小子集 | 从普通 Go 环境构建，并通过该子集的转译与诊断测试 |
| C1：逐模块迁移 | C0 把迁移后的 `.gox` 前端生成 Go，再由 Go 工具链构建 | 同一测试集通过；未迁移模块继续正常 Go 互操作 |
| C2：自编译验证 | C1 编译同一份 goxide 编译器源码，再经 Go 构建 | 归一化生成结果与回归行为一致，并可追踪差异 |

初期自举子集应先确定类型、函数、包、控制流和需要的 trait / enum / match。宏相关实现可以待卫生协议稳定后迁移；具体子集与迁移次序尚未冻结。将 `.go` 改为 `.gox` 后缀并不足以迁移，严格初始化、pub、raw Go 调用和权限规则都可能需要源码调整。

保留可由纯 Go 构建的种子版本是建议的恢复与发布策略。种子保存方式、生成源码是否提交、普通 Go 依赖及生成适配包如何随产物复现、版本锁定与升级步骤均待包 / 发布设计。C1 与 C2 的比较也要固定工具链和输入，避免格式化版本或不稳定标识符造成无意义差异。

只有完成这些构建与回归，才能宣称某一子集或整个编译器已自举；当前的手写 Go 降低示例不构成 C0，也不构成自举验证。

## 7. Rust / LLVM 到 Plan 9 汇编的讨论结论

此前讨论过“通过 Rust 工具链生成 Plan 9 风格汇编，再加入 pub Go 包装并执行 go build”。后续已明确以普通 Go 转译器为基础，因此这条路线**不属于首版主线**；是否研究独立后端是未定的后续问题。

主要障碍不在于把指令文本改成另一种汇编拼写。Go 官方汇编说明专门规定运行时如何获得参数、结果与栈帧中的指针信息；Go 内部 ABI 也明确可能随版本变化。据此，本设计判断普通 LLVM 输出加几层公开 wrapper 不能自动满足 Go 调用约定、栈移动和 GC 协调要求。[Go 汇编与运行时协调](https://go.dev/doc/asm#runtime)、[Go 内部 ABI](https://github.com/golang/go/blob/master/src/cmd/compile/abi-internal.md)

将来仍可单独研究边界明确的计算核：以普通 Go 包装隔离数据与调用，限制 GC 可见指针、分配、回调及运行时交互，并逐平台验证。它是否值得实现、如何选择代码生成器与稳定 ABI，目前没有决定，也不是实现 goxide 基础语言的前置条件。

## 8. 实现与交接验收

- 编译器原型应有完整的“goxide 输入 → 源级检查 → Go 输出 → Go 构建”闭环，以及被拒绝程序的源级诊断。
- Go 复用库的版本和边界可检查；不把 parser、类型库、gopls 或 race detector 的能力夸大成已有 goxide 语义。
- LSP 和构建对相同配置产生一致的符号、实现选择和诊断；源位置可穿过宏与降低过程。
- 自举阶段记录具体输入版本、种子、工具链、生成结果与实际回归；未完成阶段明确保留未完成状态。
- 另一台机器应能根据仓库的依赖、构建与发布说明复现所处阶段；不能依赖未交付的本地 marker 文件、临时模块或私有缓存。

这些是未来实现条件，不是当前通过的端到端测试。总体排期与状态由[设计总纲](overview.md)及[路线图](https://github.com/goxide-lang/goxide/blob/43f930c2f0fd516c263f5c71b9205279af836393/ROADMAP.md)统一维护，本篇保留架构理由和各阶段的判断标准。
