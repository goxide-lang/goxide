# 语言设计与编译原理

这组文档面向需要理解语言规则、实现编译器或审查生成代码的读者。快速开始通过一个完整项目演示用法，使用文档解释日常配置和命令；设计文档定义语法、语义判断及输入到输出的变换。

## 三种不同的命题

```text
Parse(s) = A                 字符序列 s 被解析为语法树 A
Γ ⊢ A ok                     在环境 Γ 下，A 满足类型和语言约束
Lower(A, Γ) = G              已检查的 A 被降低为 Go 程序 G
```

这三个命题不能互相替代：解析器识别一段语法，并不意味着类型检查器已经支持该构造；生成的 Go 能编译，也不能单独证明借用权限、穷尽性或卫生规则正确。当前实现范围由[能力状态表](../mvp-gap-audit.md)描述，语法文档会分别说明解析和后续检查的边界。

RFC 保留提案与历史取舍，其标题或历史“已实现”段落不自动定义当前管线的能力。阅读旧表示时，以对应的现行表示规范和已确认决策为准。尤其是用户 enum 与支持库 Option/Result 当前使用不同表示，不能将两者的降低规则混用。

## 如何读形式规则

本文档使用可复制的纯文本数学记号。`Γ` 表示名字或类型环境，`Σ` 表示声明与实现信息，`C` 表示编译配置；具体页面为每个记号给出定义。

```text
前提₁    前提₂    …    前提ₙ
──────────────────────────  [规则名]
            结论
```

横线上是规则成立所需的条件，横线下是可推出的结论。没有满足前提的规则时，编译器应诊断或转交已声明的检查阶段，不能靠某个 Go 表示“碰巧能编译”接受它。

```text
s ⇓ (v, trace)       源程序求值得到 v 和可观察事件序列 trace
G ⇓ (v′, trace′)     生成程序的对应执行
v ≈ v′              两种表示携带相同的源级值
trace = trace′      I/O、调用顺序及其他约定的可观察行为相同
```

这是解释降低正确性的记号，不是声称已经完成全语言的机器化证明。具体实现通过源级检查、生成 Go、真实执行与行为测试验证。规则中的临时名字是示意，真实生成代码可以使用不同名称。

## 输入到输出的设计要求

每个 RFC 的核心应回答下列问题：

1. **输入域**：接受哪一类 AST、类型、配置和依赖信息？
2. **前提与判断**：什么条件下接受，什么条件下报错？
3. **输出构造**：生成哪些 Go 声明、语句、表达式或文件？
4. **保持的性质**：求值次数、先后顺序、返回与跳转、存储身份、权限分别怎样保持？
5. **反例**：去掉某个前提会产生哪种错误输出或可观察差异？

[enum RFC](../rfcs/0008-enums.md)、[match RFC](../rfcs/0009-match.md)、[宏 RFC](../rfcs/0011-macros.md)与[配置和项目 RFC](../rfcs/0022-project-toolchain.md)提供形式模型及具体转换。其余 RFC 的输入/输出例子可以结合[共同转译约束](../rfcs/0018-lowering-contract.md)阅读；新增规则使用同一套[RFC 模板](../rfcs/TEMPLATE.md)。
