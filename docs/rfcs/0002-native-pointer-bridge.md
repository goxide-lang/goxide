# RFC 0002：原生类型安全指针桥接与低噪声锁诊断

状态：2026-10-01，**候选，待用户确认**。遵循 D19 warning-first；细化 U15，不静默修改 D11。只讨论 Go 互操作及机制夹具，不实现编译器。风险分析部分按 D20 仅属独立长期工作线，不是 MVP 桥接前置条件。本页 `hgo` 是完整调用场景的语义写法，包名用 import 别名表示；类型拼写与桥接元数据尚未冻结。

## 1. D11 的意图与技术边界

D11 要求拆分后的引用经显式 unsafe AsPtr 导出统一 Ptr，保留显式类型/权限边界。它不是“所有 Go 指针操作都在 Go 的 unsafe 包里”。当前机制 `type Ptr[T any] *T` 与 `*T` 的同元素类型转换是普通 Go 转换，保留 nil 和地址，不需要 unsafe.Pointer，也不把内存解释成另一个类型。

| 操作 | 处理原则 |
| --- | --- |
| 普通 `*T` 入参/返回、同元素类型的 Ptr 转换、slice/map/接口赋值 | 按真实类型处理；可能有别名与业务风险，但无摘要不是 unsafe 理由 |
| `&T` 只读视图传给允许写的原生指针位置 | 不能擦掉只读权限；直接隐式桥接是类型权限 error，可用真正可写值或已声明只读入口 |
| 原生 nullable 指针提升为非空 Arc/引用 | 不自动提升，需具体检查/构造；判空不证明独占或同步 |
| uintptr/unsafe.Pointer 地址操作、跨类型内存重解释、cgo 特殊存活操作 | 保留明确 unsafe 边界；必须逐项定义，不因本 RFC 获得授权 |
| 显式用户 unsafe callable、D11 的 as_ptr | 未决前维持已有显式规则；也不因名称叫 Ptr 就把普通传递改为危险操作 |

缺少效果信息时，把原生 `*T` 参数视为可读写、可留存的真实指针能力，不猜测只读；已有 `mut& T` 或保留真实可写能力的原生指针可以传递，不要求唯一性；不能把 `&T` 或仅表达共享身份的 Arc 自动升级为写引用。Arc 的引用获取方法/协议仍未定；它属于引用获取层，不由 U15 边界桥接代为定义，不能凭后端同为 *T 省略该步骤。只读入口可有局部 declare 描述真实行为。未知参数效果不产生默认 warning。

### 1.1 写引用核对：省 AsPtr，不省 mut

```hgo
var count int64 = 0
atomic::StoreInt64(mut& count, 7) // A 候选：显式创建写引用
p := mut& count
atomic::StoreInt64(p, 8)          // p 的类型已经是 mut& int64，不重复取址
r := &count
atomic::StoreInt64(r, 9)          // 类型权限错误，不能降级为别名 warning
```

上面合法调用的 Go lowering 是 `atomic.StoreInt64(&count, 7)`：Go 没有 `mut&` 语法；写权限先在 hgo 类型检查中确认，生成 Go 后不保留该字面标记。不能由 Go 输出倒推源语言允许 `StoreInt64(&count, 7)`。

未知效果的原生 `*T` 位置按可写能力要求检查。只读桥接只能根据明确选定的只读声明视图/内建契约，或将来已验证的具体实现依据；不得根据 Load/Get 名字、返回值类型或缺少摘要猜测只读。例如可审核 `atomic.LoadInt64` 并提供 `declare func atomic::LoadInt64(p &int64) int64;` 的候选只读视图，此时 `LoadInt64(&count)` 可用；声明需绑定真实符号/版本，正确性由声明作者负责，单纯 Go 签名匹配不证明只读。未提供该视图时本页仍写 `LoadInt64(mut& count)`。这不要求 MVP 实现效果分析。

返回/回调/函数值适配也不能洗掉权限：返回 `&T` 的 helper 不能被改成返回 `mut& T` 或可写 Ptr；明确可写实参只在实际满足权限时降为只读；原生 nullable 返回值不自动成为非空写引用。对只读源接收者做接口装箱也不能借恢复 Go *T 方法集暴露可写方法。原生 `buffer`/`port` 示例保留的是原生类型自身已有能力，不能外推到只读 hgo 视图。D11 明确 unsafe 权限擦除与普通桥接仍分开，本次核对不是对方案 A 的批准。

### 1.2 先取得内部引用，再讨论 Go 桥接

用户已明确这两个层次必须分开；这项分层不等于批准 A，也不新增任何容器取引用协议。

| 当前持有的值 | 取得引用的完整链路或不适用情况 | 引用指向什么 |
| --- | --- | --- |
| 可寻址、可写的 `value: T` | `mut& value` → 已有 `mut& T` → A 候选桥接至 Go `*T`（或按现行明确边界转换） | value 本身就是 T |
| `boxed: Boxed[T]` | Boxed 尚不是已定义类型；现有专题只有未定的 Box。须先由其未来明确的方法/协议取得 `mut& T` → 才能进入桥接。当前没有可引用的准确方法名，不能写出声称可用的调用 | `mut& boxed` 是容器/句柄绑定的写引用，不是内部 T 的写引用 |
| `ref: Ref[T]` | 旧共享 Ref 已由 Arc/引用方向替代，没有现行 Ref 取写引用方法。如果用户指实际的 `r: mut& T`，它已是引用，直接传 r；若是 `r: &T`，不能升级成可写 | `mut& r` 针对引用绑定槽位，不会赋予它所指 T 的写权限 |
| `arc: Arc[T]` | Arc 表达共享身份；须通过该类型明确支持的方法/访问协议取得内部引用。普通 Arc 的取写引用方法尚未定义，因此不能提供任意 `arc → mut& T` 调用。若协议仅给 `&T`，只走匹配的只读入口 | `mut& arc` 是 `mut& Arc[T]`，不等于 `mut& T`，不会自动拆句柄 |

现有可准确引用的访问协议是锁专题的 `.do` / `.write` 回调，不是 Boxed/Ref/Arc 的假想 `as_mut`：

```hgo
var count int64 = 0
p := mut& count
atomic::StoreInt64(p, 7) // T → mut& T → A 候选桥接

locked := Lock.new(int64(0))
locked.do(|p| {
    atomic::StoreInt64(p, 7) // Lock 协议已给出 p: mut& int64 → A 候选桥接
})
```

这里 `locked` 是现有 Lock 句柄，不能把例子重写为 `arc.do(...)`：没有定义这样的 Arc 方法。若持有 Arc 包裹的某种同步对象，也必须先按其既有接口取得访问入口，不能假设自动解包或把 Arc 与 Lock 等同。

引用获取方法可以选择回调式、返回式或不提供写访问；本次不选择这些新协议。A/B 都只处理之后的边界转换，不能替调用者插入取址、解包、加锁或权限提升。原生 Go 指针保留真实类型往返是另外一种已有原生值流转，不构成容器到 `mut& T` 的捷径。只读桥接同样先取得类型自身允许的 `&T`，再使用匹配的只读契约。

## 2. 两种可实现方案

### A：在原生边界自动做同类型桥接（推荐）

只在已解析的原生函数/方法、原生接口赋值或已知函数签名位置插入合法桥接，表达式求值一次。用户不需要先建 Ptr 中间变量。桥接是编译器内建规则，不搜索任意 AsPtr trait，不执行自定义转换方法：

```hgo
import atomic "sync/atomic"
import flag "flag"
import bytes "bytes"
import io "io"

var count int64 = 0
atomic::StoreInt64(mut& count, 7)
observed := atomic::LoadInt64(mut& count)
// Load 用 mut& 仅因原生 *int64 位置未描述只读；不是证明其实现会写。

fs := flag::NewFlagSet("app", flag::ContinueOnError)
port := fs.Int("port", 8080, "port number") // 原生可空指针视图，不自动变 Arc
parseErr := fs.Parse([]string{"-port=9090"})
// 保留 parseErr；读取 port 按原生可空指针语义，不自动插入非空承诺。

buffer := bytes::NewBuffer([]byte{65, 66})
var reader io::Reader = buffer // 按真实 Go 方法集，不搜索 hgo trait wrapper
output := make([]byte, 2)
n, readErr := reader.Read(output)
```

Lowering 是正常的 `atomic.StoreInt64(&count, 7)`、`fs.Int(...)`、`var reader io.Reader = buffer` 等。已有 Ptr 可在单层参数处显式转回 `*T`；后端若本来保存原生指针则直接传递。返回类型保留原生身份、nil 能力与真实方法集；在 hgo 类型系统用原生视图元数据表达，不增加一个通用 safe `*T` 类型，也不隐式赋给 Arc。

**对 D11 的改变必须批准**：这是允许实际已取得的 `mut& T` 在指定原生边界不经用户显式 unsafe AsPtr 的窄例外。显式 `as_ptr()` 仍保留 D11，用户自定义 AsPtr 不参与隐式选择。若仅修改实现而不记录这项语义例外，就是绕过旧决策，本 RFC 不这样做。

### B：类型保持的显式 AsPtr 改为普通操作

改写 D11，将精确同类型、保留 nil/地址的 as_ptr 变成普通操作；真正权限绕过或内存重解释另用明确 unsafe 操作：

```hgo
var count int64 = 0
p := (mut& count).as_ptr()     // B：普通操作，显式形成 Ptr[int64]
atomic::StoreInt64(p, 7)      // 根据真实参数做 Ptr[int64] → *int64
observed := atomic::LoadInt64(p)

buffer := bytes::NewBuffer([]byte{65, 66})
var reader io::Reader = buffer // 原生返回视图仍按真实方法集
```

`&T` 不能因使用同名 as_ptr 而导出可写能力：B 必须撤销只读引用上的普通可写导出，保留明确 unsafe 权限擦除，或另提供只读原生视图；不能只删除 unsafe 关键字而保持旧的全部实现。Ptr 的显式中间值会使指针回调/容器写法更繁琐；普通 Ptr 与原生指针函数类型不同仍要函数桥接。

| 比较 | A：原生边界桥接 | B：普通显式 AsPtr |
| --- | --- | --- |
| 用户体验 | 常见调用接近 Go，不反复命名 raw 值；只读到未知可写位置需明确处理 | 转换点可见，但多一层语法；只读例外仍需记忆 |
| D11 变更 | 增加窄边界例外，保留显式 AsPtr 原语 | 直接修改 AsPtr 的 unsafe 属性及只读实现集合 |
| 实现 | 类型检查后 IR 插入 bridge；单层简单，接口与函数需按真实身份处理 | 显式调用较易定位，但仍需 Ptr 与原生函数/容器兼容处理；不是全部转换自然相容 |
| 性能 | 单层不复制对象；函数适配可形成闭包，分配须测量 | 同样；中间 Ptr 通常可消去，但不承诺零分配 |
| 诊断与维护 | 精确报源类型/目标类型，避免用户方法参与隐式转换；需维护边界位置规范 | 转换点易定位，需迁移已有 unsafe AsPtr 及审查只读能力擦除 |
| 未来可选分析的误报/漏报 | 两者都只按已知访问/协议风险 warning，不因桥接本身报警；外部隐藏行为会漏报 | 同左，不让显式转换点变成批量警告点 |

推荐 A。保留 D11 原样、每次用 `unsafe ...as_ptr()` 或逐函数 declare 是可维持旧行为的回退，但不作为正常互操作的推荐体验。唯一待确认项是是否批准 A 的窄例外；不要求用户同时决定整个生命周期或递归 ABI。

## 3. slice、map、接口与回调不是递归强转

实际 Go API：`bytes.NewBuffer([]byte) *Buffer` 保留传入存储，`Buffer.Bytes() []byte` 返回别名；`flag.(*FlagSet).Int(...) *int` 返回可继续使用的配置槽位；`sort.Slice(any, func(int,int) bool)` 原地重排容器并调用比较器。以上签名/行为已读本环境 Go 1.27.1 源码 `src/bytes/buffer.go`、`src/flag/flag.go`、`src/sort/slice.go`，由下列夹具核对所覆盖机制，不泛化到整个包。

```hgo
import sort "sort"
items := []*native::Item{first, second} // 原生类型视图示意，保留真实 []*Item
sort::Slice(items, func(i int, j int) bool {
    return items[i].Rank < items[j].Rank
})
```

原生容器可以原样往返；不把 `[]*T` 重写成 `[]Ptr[T]`，也不把 `map[string]*T` 重写为另一张 map。若用户明确要求不同元素类型的容器，必须用显式逐元素适配或提供具体转换；不能用 unsafe.Pointer 强转，也不能静默复制破坏共享身份。比较器同步调用、原地排序不意味着不能有指针；具体并发修改或重入链才 warning。

常见回调形状 `func(*bytes.Buffer)` 的 hgo `func(Ptr[bytes.Buffer])` 不是同一个 Go 函数类型。A/B 均可在已知目标签名生成 `func(p *bytes.Buffer) { callback(Ptr[bytes.Buffer](p)) }`。桥接先对回调表达式求值一次并保存函数值，再判断 nil 和捕获该值，不能捕获之后可能重绑定的源变量槽位。nil 函数值须保持 nil，不能总包成非 nil 闭包；闭包留存/指针结果照原生语义，缺效果摘要不拒绝。明确 unsafe callable 属性不能被桥接擦除，须保留属性或由显式有体包装承担调用；这是类型/明确操作检查，不是长期别名分析。参数权限方向要分别检查：只读参数回调可以接收可写对象的降权限视图；要求可写参数的回调不能放到只保证提供只读对象的位置。nullable 是独立维度，不能无检查地把原生 nullable 入参适配为非空 &T/mut& T。

接口装箱同样保持原生动态类型和 typed nil；桥接 `Ptr[bytes.Buffer]` 到 io.Reader 时先恢复真实 `*bytes.Buffer` 才检查方法集，不给具名 Ptr 伪造接收者方法，不隐式选 hgo trait 实现。类型不匹配是 error，不用 warning 掩盖；未知 nil 风险也不默认逐个报警。

## 4. W01 收窄：先有协议，再有使用风险

前轮“锁内引用一离开就 W01”过于宽泛，现不作为默认告警条件。只记录来源，不因跨词法范围暗示内存失效：

1. 能追踪到保护对象及其协议，并看到回调外使用/留存违反具体协议，才给 W01。例如某 API 明确约定回调后不得保存；或已知解锁后通过方法值直接写原对象。单纯返回普通 GC 指针不报。
2. 已知后续访问由同一锁保护，或所有访问采用同一个正确原子协议，不报 W01。不能只看访问地点“在另一个回调里”就取消，必须关联同一锁/同一存储。
3. 来源或后续用途未知、只是导出一个指针/方法值/error/panic 载荷，不报默认 warning；可在按需分析说明中标注未知，不形成安全证明。确有声明的“不留存”协议时，载荷越界本身是具体违约证据，可告警。
4. 同一风险还满足 W02/W03 时合并，优先显示冲突/绕锁的实际访问点。函数摘要是可选精度改进，不把未导出摘要变成编译错误。

```hgo
p := lock.do(|value| { return value }) // 仅返回：记录来源，不报
lock.do(|_| { *p += 1 })              // 同一锁保护该存储：不报 W01
*p += 1                               // W01/W03 合并：已知绕开同一锁写
```

第三行是协议风险，不等于已发生 race；若其他访问实际全串行，用户可注明/抑制。复杂外层锁或自定义原子包装可能误报，隐藏外部访问可能漏报。返出的 p 如果指向被替换掉的旧存储，要追踪真实对象身份，不能仅凭同一个变量名套用保护关系。

```hgo
p := lock.do(|value| { return value })
atomic::StoreInt64(p, 1)
x := atomic::LoadInt64(p)
```

若所有对此 int64 的访问（包括锁内）都使用相容原子操作，且对齐/发布满足目标平台要求，则无需 W01；锁的存在不禁止另一种已知协议。若锁内普通读写与锁外原子读写并发混用，单边原子不够，W02 给出两侧证据。更换同步协议、任意外部访问未知时不宣称已经证明无竞争。

## 5. 机制证据与实现边界

`tests/design/ptr/interop_test.go` 验证原子指针入参、flag 指针返回、bytes slice 别名及 io.Reader、原生指针容器排序、函数适配保持 nil。`tests/design/lock/boundary_test.go` 的同锁返回引用使用对照验证正常同步路径。都不使用 unsafe 包或发起数据竞争；它们证明 Go 机制可行，不是已经实现 A/B 的 hgo 类型检查或 W01 消噪。

对齐、方法集与 nil 等已知约束保持真实 Go 语义。静态成本和闭包分配未基准测试；Go race 仅验证实际执行路径。独立审查与文档检查不能替代未来前端针对只读擦除、nullable→非空、函数 nil、容器身份和自定义 AsPtr 副作用的正反例。

## 6. 分析复杂度与 MVP 边界

**用户最新决定：别名/借用风险静态分析是独立长期工作线，完全不属于 MVP 完成条件，连 W01–W04 的一个子集也不要求先实现。** 本文的桥接类型规则属于语言设计；W01 消噪属于未来诊断设计，不能将二者绑成同一个交付门槛。

warning 只改变错误处理策略，不会使分析自动变容易。下面是长期研究的成本分层，不是 MVP 计划或工期承诺：

| 未来范围 | W01–W04 能处理什么 | 成本及依赖 |
| --- | --- | --- |
| 函数内直接证据 | W01 已知锁对象外直接访问；W03 局部 map/slice 别名绕锁；W04 已知同锁直接嵌套；W02 仅直观捕获读与父任务写候选 | 中等。仍需类型化 IR、CFG、分支/循环合流、稳定位置与对象身份、闭包/defer/panic 表示；简单源码扫描不足。每规则可独立研究，不承诺都做 |
| 有限本地函数摘要 | helper 参数/结果来源、已知闭包与锁对象传播，减少重复误报 | 中高。需摘要组合、递归预算、失效和可信外部契约；不因摘要缺失拒绝用户代码 |
| 跨包与动态调用 | 接口目标集合、共享堆图、反射、递归容器、自定义同步/原子混用及一般 happens-before | 高至很高，暂缓。低误报并发分析是长期课题，当前不值得为 MVP 搭建全局 effect/别名系统 |

函数内分析也不是简单廉价功能：控制流不可达、重绑定、底层数组变化和隐藏回调都可能误导来源链。即便只做 warning，也要设计不应报告对照、说明分析盲区。未来结合 Go race 验证实际路径，而非把静态分析当作动态验证替代。

Rust 官方记录 NLL 随 Rust 2018 引入，并在 Rust 1.63 完成所有 edition 默认切换；这说明借用检查有迁移与兼容性工程，不能据此断言“几十版本才凑合”，也不能直接换算本项目工期。[官方 NLL 说明](https://blog.rust-lang.org/2022/08/05/nll-by-default/)。本轮不继续扩展历史调研。

其他语言模块只需考虑这些自然的可分析性接口，不提前实现分析器：

- 桥接保留真实类型、nil 能力、调用目标及转换来源；未知效果不要求用户增加注解。
- trait/宏保留选定 impl、符号身份、展开与源码映射，不以字符串拼接擦掉语义。
- 明确赋值是否复制值/句柄、回调求值顺序、panic/defer、锁释放时点；这是语言语义本身的需求。
- 正常类型检查与可选未来 warning 分层。无需 MVP 建来源集合、堆别名图、效果摘要或完整控制流风险分析；只有其他实现真正需要时才建设相应 IR/CFG。
- 测试将 Go 机制证据、语言类型正反例及未来分析器诊断测试分开；当前夹具不充当长期工作线的完成证明。

独立复审已修正回调参数权限方向、桥接函数值求值一次/按值捕获、nil 以及明确 unsafe 属性保留；没有把长期风险分析作为 MVP 要求。

后续持有者接口与指针功能拆分见 [RFC 0003](0003-pointer-roles-and-mvp.md)。本篇 §1.2 记录此前尚无取引用 API 的状态；新文仅提出候选，未批准任何方法或自动桥接。当前优先评审功能与持有层必要性，不催定 A。
