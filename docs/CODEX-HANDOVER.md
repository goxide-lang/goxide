# 交接：把剩下的工作交给 Codex 独立完成

写给接下来独立推进本仓库的 Codex。读完这份，再读 `AGENTS.md`、`docs/pre-mvp-plan.md`、`docs/development-plan.md`，三份合起来就是你需要的全部上下文。

## 一、项目是什么

Goxide 是把 `.gox` 转译成普通 Go 的语言：卫生宏、闭合 enum 与 match、Option/Result 与 `?`、显式 trait/impl、派生、读写引用区分，同时保留 Go 的运行时、工具链和生态互操作。设计目标三项目标是安全性、显式实现与可读性、Go 互操作。

**最容易跑偏的地方**：这个项目的历史包袱几乎全部来自"为将来兼容"。你接手时的仓库里有一份 4 万行的旧管线、一堆证据文件和免责式文档，都是这么长出来的。你的任务包括把它们删掉，而不是维护它们。判断标准很简单：**如果一段代码是在为"以后可能需要"服务，删掉它。**

## 二、当前进度

已完成：新前端的 `syntax`（token/lexer/ast/parser/printer）、`expand`（宏展开与卫生）、`resolve`（名字解析含卫生上下文）、`check`（穷尽性等六项检查）、`lower`（纯 Go 子集 + enum/match/`?`）。

管线：`parser.ParseFile → expand.Expand → resolve.ResolveExpanded → check.Check → lower.Lower`。

分支状态：工作都在 `feat/syntax-frontend` 上，链式包含 `docs/org-transfer-links`、`chore/gate-simplification`。都还没 push。

剩余阶段见 `docs/pre-mvp-plan.md`：P2 宏接入与派生、P3 引用与投影、P4 trait/impl、P5 最小项目工具链、P6 CLI 切换与删除旧管线、P7 收口。P6 之后再按 `docs/development-plan.md` 的 MVP 阶段重启 workspace、`import-go`、vendor、构建脚本、LSP。

## 三、怎么工作

每个阶段固定四步：**改规范 → 写提示词 → 一次做完 → 验收提交**。

- **先改规范**。涉及语言语义或表示的，先写进 `docs/design/` 或 RFC。没有规范不要开始写代码，否则你会在实现里发明语义，而语义是这个项目唯一不能自己发明的东西。
- **一次给足范围**。不要拆成"里程碑交付"。上一个阶段我一度把语言核心拆成三个里程碑，被用户否掉了，理由正当：拆分交付是为了降低模型能力的风险，而这不是风险所在。
- **验收必须自己跑**。`go build ./...`、`go test -count=1 ./internal/... ./tests/...`、`go vet ./internal/... ./tests/...`、`gofmt -l internal cmd`。沙箱里默认 Go 缓存可能不可写，用可写的 `GOCACHE` / `TMPDIR`，但报告里要写清实际用了什么命令。
- **行为类要求必须真运行**。`lower` 的端到端测试会生成临时模块、调 `go build` / `go run`、比对运行输出与手写 Go 版本。后续阶段照这个标准做，不要退化成只比字符串。

## 四、硬约束（违反即返工）

1. **不写兼容层**。不要旧格式检测、版本号、指纹、迁移路径、适配层。项目 pre-1.0，没有外部用户，破坏性变更直接改。
2. **不写第二个实现**。新管线不调旧管线，旧管线不为配合新代码改造。两者靠目录隔离，P6 一次性删掉旧的。
3. **不抽没有第二实现的接口**，不超过三层间接，不做可配置的注册表。
4. **不放宽测试**。既有测试失败就去修实现。唯一允许的测试改动是"特性从未支持变为已支持"导致的拒绝用例删除，那种情况要在提交信息里写明。
5. **不改相邻仓库**。`../std` 和 `../serde` 有各自的发布节奏；需要它们配合时先提出来。
6. **不写额外文档**。不加评审报告、证据文件、验收记录。只更新状态表和对应的一份设计文档。
7. **只改任务点名的目录**。越界改动要单列并附最小复现。

最容易犯的三条：把"稳妥"读成"多写一层"；顺手重构未要求的东西；为了让测试变绿而放宽断言。

## 五、几个已经定死的技术决定

- **enum 表示**：密封接口 + 每变体一个指针结构体，标记方法未导出（`is<Enum>`）。跨包闭合靠 Go 自己的规则，**不需要任何元数据**——旧管线那 960 行的 `enum_artifact.go` 和 `enumMetadataVersion = 9` 在新管线里完全不产生、不读取，P6 删掉。详见 `docs/design/enum-representation.md`。
- **nil 不是合法 enum 值**。每个 `match` 在分派前检查接口，命中即 panic；用户写的 `_` **不兜 nil**。穷尽性由 `check` 保证，不指望 Go 编译器。
- **match 一次分派**。外层 `case` 一个变体，同一变体内多条 arm 在内层按源码顺序落成 `if / else if / else`。不要回到"先取标签、再分支、再投影"的多段式。
- **宏名字解析**：路径默认按**定义点**解析，`$caller::` 显式指调用点。这与 Rust 默认相反，理由是不想让调用点的同名项被静默绑定。改造方向时源级写法不变。
- **`pub` 是唯一可见性标记**。Go 写法的声明暂时兼容"首字母大写即公开"（将来可关），新语法（`struct` 糖、`enum`、`trait`、`impl` 成员、`use`、`mod`、宏）只认 `pub`。
- **`pub` 小写名只生成一个大写名**，不保留小写实现加大写包装。函数身份要唯一，不要包装帧。
- **`std/sum` 保留当前 tagged struct 表示**。用户 enum 走类型断言，Option/Result 走 `sum.Tag*`，现有 `Tag` / `Value` / `Project` / `Validate` API 保留。密封接口统一安排在 MVP-6，与 safe std 一起验证变体携带完整泛型参数及公开 Go API 的变更。
- **`Option[T]` 不做指针特化**。`T` 自身可空时无法区分 `None` 与 `Some(nil)`，代价不值得。

## 六、验收与提交

提交前自己核这七项：

1. 四条验收命令自己跑过。
2. `git status` 确认改动范围在允许的目录内。
3. `git diff` 里没有既有测试被改松。
4. 生成的 Go 是"普通人会手写的样子"——没有多余包装、转发函数、未使用的辅助类型。
5. 端到端真的调了 `go build` / `go run`。
6. 没有引入版本号、指纹、兼容分支、可选配置项。
7. 同一输入两次生成字节一致（`lower` 已有该断言，保持）。

一个主题一个提交，提交信息写"为什么"而不是"改了哪些文件"。分支按 `docs/*`、`chore/*`、`feat/*` 分开，链式推进时后一个包含前一个。

**不自动 push、不开 PR、不合并、不改分支保护**——这些由用户决定。

## 七、需要停下来问用户的三类事

只有这三类：

1. **用户可见的语言语义**：语法、求值顺序、错误行为。
2. **破坏相邻仓库或发布契约**：`std`、`serde` 的改动。
3. **与已确认决策冲突**：`docs/design/decisions.md` 里标记为已确认的条目。

其他一切按"最简单的解释"继续做，并在报告的"未完成与假设"一节里记一行你选了哪个解释。这条很重要：停下来问的代价比选错一个可逆的默认值高得多，而绝大多数决定都是可逆的。

## 八、最后

这个项目的病根是**广度优先**：宏、enum、项目工具链、网站、workspace、迁入工具、构建脚本授权，一应俱全，但没有一个能真正用起来的端到端闭环。你接手时的重点不是"再加一个特性"，而是**让已有的东西一条条真正跑通，并把没用的东西删掉**。

判断做得好不好的标准不是新增了多少代码，而是：**能不能用 Goxide 写一个多包程序，编译、运行、测试都通过，而且生成的 Go 读起来像人写的。**

`AGENTS.md` 末尾有一份自检清单，写代码前和交付前各过一遍。
