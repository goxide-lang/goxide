# 在已有 Go 项目中使用 Goxide

`goxide gen` 将一个包里的 `.gox` 转成同目录的 Go 文件。保留现有 `go.mod`、手写 Go 与构建流程，用 `go generate` 在选定包中加入 enum、match、宏或派生。

## 五分钟上手

按[安装说明](website-guide.md#安装)从当前编译器源码构建 CLI。将 `goxide` 与 Go 加入 `PATH`，核对 `goxide --version` 显示的构建工具链与 `go version` 完全一致，包括补丁号；安装页给出对应版本与完整构建命令。以下用一个空目录演示；已有项目直接在目标包添加两个文件中的相应内容。

```sh
mkdir trygen
cd trygen
go mod init example.com/trygen
```

手写 `main.go`，保留类型、函数与 Go 入口：

```go
package main

import "fmt"

//go:generate goxide gen .
type Order struct { Total int }
func total(order Order) int { return order.Total }
func main() { fmt.Println(classify(Order{Total: 42})) }
```

新增 `order.gox`，直接引用同包的手写类型和函数：

```gox
package main

enum Decision { Accept(int), Reject }
func classify(order Order) int {
    return match Decision::Accept(total(order)) {
        Decision::Accept(value) => value,
        Decision::Reject => 0,
    }
}
```

```sh
go generate ./...
go build ./...
go run .                 # 输出 42
go generate ./...        # 输入不变时，order_gox.go 字节不变
```

`go:generate` 使用 `.`：Go 不通过 shell 执行它，`*.gox` 不会展开。`gen` 与 `transpile` 是同一命令的两个名称；默认原位生成，`-o -` 可将单个 `.gox` 的结果写到标准输出。

## 按 feature 选择代码

在每个包的生成命令中指定配置：

```go
//go:generate goxide gen --features=json,trace .
```

`.gox` 用 `#[cfg(...)]` 选择完整顶层声明，用 `#[cfg_attr(...)]` 选择属性：

```gox
use std;

#[cfg(feature("json"))]
func Encoding() string { return "json" }

#[cfg(not(feature("json")))]
func Encoding() string { return "plain" }

#[cfg_attr(feature("trace"), derive(std::derive::Debug))]
type Message struct { Text string }

const HasJSON = cfg!(feature("json"))
```

原生 Go 模式缺省不启用 feature，未启用的合法名称查询为 false；配置只作用于当前生成包。支持 `all(...)`、`any(...)`、`not(...)` 组合。`cfg!` 只生成布尔常量，`if cfg!(...)` 的两支仍检查；引用条件声明的代码也要放进对应 cfg 声明中。

切换 feature 后重新 `go generate`，再 build/test。包内使用条件编译时，原位生成必须用目录输入，确保所有 `_gox.go` 同时切换配置；某源文件的声明全被关闭时会生成包壳，覆盖旧声明。`gen --features=json -o - file.gox` 可单独预览。Go build tags 与 feature 独立；`--no-default-features` 用于有 `[features]` 声明的 TOML 项目。完整规则见 [RFC 0022](rfcs/0022-project-toolchain.md)。

## 目标与环境条件

原生 Go 包和单文件的 `gen/transpile` 继承当前 Go 环境的 GOOS/GOARCH，包括 `go env -w` 保存的默认值，不接受 --target。`-o` 不改变这条规则。条件可写 `target_os("linux")`、`target_arch("arm64")`、`target_platform("unix")`、`target_endian("little")`、`target_pointer_width("64")`，参数区分大小写。

`env("APP_EDITION")` 查询启动时是否设置变量，`env("APP_EDITION", "pro")` 比较原值；不需要清单或 CLI 登记。空串算已设置。切换环境值后重新整包生成，Go build 不会自动重新求值。

```sh
GOOS=linux GOARCH=arm64 goxide gen .
goxide env --json
goxide env --json APP_EDITION
```

TOML 项目的 gen/transpile，以及所有输入的 expand/build/run/test，使用工具链目标：缺省为运行 Goxide 的宿主，可用 `--target arm64-unknown-linux` 或等价的 `--target linux/arm64`。可跨目标生成或 build，非宿主 run/test 提前拒绝。`goxide env --list` 列出值域和可用组合；`--go` 对所有编译入口生效，所选 Go 版本须与 Goxide 的构建工具链一致。

## 共存规则与摩擦点

同目录、同包的手写 `.go` 只读加入类型检查，`.gox` 可引用其中的类型、常量和函数；手写 Go 也可调用生成声明。`gen .` 在发布前检查生成 Go 和手写 Go 的完整函数体。`gen order.gox` 只编译并覆盖该文件，但原位生成会扫描同包 `.gox` 的配置使用；宏输入或模板含 cfg/cfg_attr 名称时也要求目录输入，以覆盖动态构造属性名的情况。引用其他 `.gox` 声明时使用目录输入。`order.gox` 对应 `order_gox.go`。生成文件带 `// Code generated by goxide. DO NOT EDIT.`；只允许覆盖带标准 `Code generated … DO NOT EDIT.` 标记的同名文件，遇到无标记的同名文件会报错。将冲突的手写文件改名，修改逻辑时编辑 `.gox`，再生成。

完整包检查需要可用的导入依赖。若导入包也要生成，先运行它自己的生成命令；可在当前包的 `goxide gen .` 指令前放置 `//go:generate go generate ./child`。各包仍由自己的命令选择 feature。

用户 enum 与 match 本身可生成不依赖支持库的 Go；Option/Result、格式化和标准派生等能力按需使用 `github.com/goxide-lang/std`，serde 派生另需 `github.com/goxide-lang/serde`。派生等库入口需要显式的 `use std;` 或 `use serde;`。缺失依赖时，诊断会给出按编译器 require pin 固定版本的 `go get` 命令；交互终端确认安装后，`gen` 会更新 `go.mod` / `go.sum` 并重试，非交互调用则退出并保留模块文件。依赖齐备后的常规生成保留 `go.mod` / `go.sum`；升级编译器及库版本后重新生成。

生成文件包含行级 `//line`，Go 编译诊断可回到 `.gox` 的源行；宏映射到可用的定义点或调用点。`go vet` 仍会检查生成文件，按诊断回到源文件修复。第三方 linter 对生成标记和 `//line` 的处理各异，按工具自身配置处理生成文件。这里没有列级调试映射或 LSP。

## 何时选择完整工具链

已有 Go 项目只在少数包试用时使用 `gen`，然后继续运行原来的 `go build` / `go test`。需要由 Goxide 按 `goxide.toml` 选择目标、管理 Goxide 多包依赖、生成独立模块并 build/run/test 时，使用完整 CLI 的项目模式。当前 workspace、vendor、构建脚本、列级 source map 与 LSP 均未开放，完整工具链也不提供这些入口；进度见[能力状态表](mvp-gap-audit.md)。

## 给 coding agent 的提示词

> 在这个已有 Go module 的指定包里局部加入 Goxide。先阅读编译器的 `docs/using-goxide-gen.md` 和能力状态表。保留 `go.mod`、手写 Go 和现有构建结构；将新增逻辑写入 `package` 声明与该包相同的 `.gox`，用同包 Go 类型和函数，并在一个手写 `.go` 文件加入 `//go:generate goxide gen .`。不要用通配符。只允许覆盖带标准 `Code generated … DO NOT EDIT.` 标记的 `_gox.go`，出现手写文件冲突时改名。按缺依赖提示和编译器 pin 补齐 std/serde。执行 `go generate ./...`、`go build ./...`、相关测试与真实运行，再次生成并比较字节。报告改动、输出和未通过检查；不引入 workspace、vendor、构建脚本或 LSP。
