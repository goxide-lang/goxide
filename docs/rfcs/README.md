# hgo 逐特性 RFC 与转译约束

每项新特性在这里单独评审：先看 hgo 输入和 Go 输出，再看必须保持的行为、拒绝例子及双向互操作。本文档目录是设计约束入口；[设计专题](../design/overview.md)保留背景与取舍，[决策登记](../design/decisions.md)维护确认状态。

## 使用规则

1. 新增或修改语言能力，先新增或更新对应 RFC。使用[模板](TEMPLATE.md)，不要只在总纲里增加一句功能描述。
2. 每篇明确区分已确认目标、暂定语法/ABI、未定问题。实现分支已有有限 hgo 端到端子集，准确范围见实现记录；有 RFC 不代表该篇所有能力已实现或整个方案已经批准。
3. 每个正例给 hgo 输入、Go 输出、预期结果及保持的性质。涉及外部包时写明生成文件属于哪个包。标明片段、伪代码、候选表示，不能伪装成已可独立编译的输出。
4. 反例注明由 hgo 前端拒绝、Go 编译器拒绝，还是运行时检查拒绝。hgo 拒绝的程序没有合法的生成输出，可列错误降低以说明禁止原因。
5. 每篇说明 hgo 调 Go 和 Go 调 hgo。编译期能力无需对应 Go 语法，但要说明其生成 API 如何使用。
6. 约束是可观察语义，通常不要求生成文本逐字一致。更换表示、消除 wrapper 或内联均不能改变选中实现、求值次数、别名、复制和控制流。
7. 例子使用稳定的局部编号，例如 `TR-01`。未来前端测试按编号绑定正例、拒绝例和行为检查；只有手写 Go 机制验证时单独标识。
8. 已确认语义与候选 ABI 冲突时，记录反例并修订 ABI。不能为了保留某段生成代码，暗中删掉源级功能或更改已确认语义。

## 范围与验证

LSP、自举、构建缓存等工程架构继续由[工具链专题](../design/compiler-and-tooling.md)管理；凡引入新源级行为或改变产物契约，仍需相应 RFC。Box、supertrait、GAT、特化、用户过程宏、锁块等未定或延期能力列在[决策登记](../design/decisions.md)，启用前必须另立 RFC，不能从名字补出未经确认的语义。

运行 `python3 scripts/check_design.py --docs-only` 检查链接、围栏及 RFC 基本结构。完整命令继续验证原有手写 Go 机制；不会自动编译这里所有 Go 片段，更不会运行尚不存在的 hgo 前端。每篇的验收表是未来实现要求，不是通过记录。

## 研究补充与同步边界

早期研究 RFC 0001–0006（含诊断业务补充）保留于 [research](research/0001-scoped-borrow-views.md)，与本目录逐特性 0001–0020 分开编号；原有链接已重定位。目录根的 20 篇继续接受唯一编号、六章节与 hgo/Go 示例检查；研究文档仍检查链接和围栏，不冒充已冻结特性规范。远端独立决定编号记 R19–R26，见决策登记。

所有借用/效果相关 RFC 受 D19/D20 约束：无法证明独占/不逃逸或缺少摘要，不是默认准入拒绝的依据；风险分析不属 MVP。基础类型权限和显式 unsafe 规则不降级。统一 wrapper（0019）和关联函数（0020）方向已同步，但对应通用前端尚未实现。
