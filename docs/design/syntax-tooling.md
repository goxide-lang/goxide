# 额外语法工具包：syntax、quote 与 syn

状态：quote / syn 风格能力放在额外包中。用户已于 2026-10-20 开始过程宏基础设计，当前候选合同集中在 [RFC 0030](../rfcs/0030-procedural-macros.md)；宿主与这些包均未实现。下文保留工具库分层背景，具体 TokenStream、卫生、登记和执行提案以该 RFC 为准。Rust 只用于参考宏工具的分层，safe 标准库另以 [Go std](standard-library.md) 为基础设计。

| 状态 | 范围 |
| --- | --- |
| 已确认 | D16：quote / syn 风格能力放在额外包；过程宏现已进入 RFC 设计阶段。 |
| 暂定 | T14：syntax 公共协议、普通工具可先于过程宏、ToTokens / quote 构造方式和实现顺序。 |
| 未定 | U11：RFC 0030 的公共协议、受控上下文与过程宏宿主提案待接受。 |

状态编号见[决策登记](decisions.md)。除已确认范围外，正文的具体规则与验收条件均为暂定方案；Go 示例验证不代表 goxide 功能已实现。

## 1. 工具库与过程宏宿主分开

Rust 的 quote 是将语法数据构造成 token 的库，也明确支持普通 main / build 工具；syn 负责将 token 解析为语法树。proc_macro2 提供可在编译器过程宏上下文以外使用的 token 表示。这说明语法工具库不必与编译期用户程序执行绑定。[quote](https://docs.rs/quote/latest/quote/)、[syn](https://docs.rs/syn/latest/syn/)、[proc_macro2](https://docs.rs/proc-macro2/latest/proc_macro2/)

goxide 分成以下层次，名称均为逻辑包名：

| 层 | 职责 | 是否要求过程宏宿主 |
| --- | --- | --- |
| syntax 协议 | token、分组、源码位置、来源及不透明卫生上下文 | 否，是编译器与工具共享的数据协议 |
| syn 包 | 解析 goxide 文本 / token，形成 AST，提供访问和重建接口 | 否，可在普通工具运行时使用 |
| quote 包 | 模板、插值、重复、ToTokens 等，构造 token 数据 | 否，可由声明宏生成普通构造代码 |
| 过程宏宿主 | 加载用户扩展，在编译期间调用其程序，检查输出并继续编译 | 是，这一执行能力后续设计 |

普通工具里的 `AST -> AST` 函数不是因为处理语法就成了过程宏。只有编译器将其作为用户宏扩展执行，才进入过程宏机制。导入 syn / quote 不自动登记或执行编译期扩展，也不自动启用构建钩子。

## 2. 首版可以先提供普通工具能力

这是暂定实现建议，不承诺全部工具能力与首个可用版本一起交付。已确认的范围是额外包方向，具体里程碑仍需选择。

普通 goxide 程序可以显式运行以下流程：

```text
文本或 token -> syn 解析 -> 工具自己的普通代码 -> quote 构造 token
                                                     |
                                        显式输出文件或交给工具消费者
```

这些步骤发生在该工具运行时，继续遵守普通 goxide 的类型、借用、依赖与 unsafe 规则。需要读取或写入文件时，由工具显式调用对应的 safe Go std 接口；库不会偷偷扫描目录、加载依赖或改写使用方源码。

普通工具可生成一个 `.gox` 文件，再由用户明确运行下一次编译。这是两次普通执行与编译，不代表 goxide 构建默认自动运行该工具。自动生成流程与构建钩子需要另外定义输入、依赖和执行规则。

## 3. quote 是语法数据构造，不是 eval

quote 包可以参考 `quote!` 的模板与 `#value` 插值形式。该形式还需与 goxide 声明宏的 `tt` 捕获、分组和重复语法接合；以下只说明拟议行为：

```goxide
// 普通工具运行时；imports 和错误处理在此省略。
tokens := quote::quote! {
    call(#argument)
}
```

该宏展开为普通的 token builder 调用。`argument` 在工具运行时经已选定的 ToTokens 实现插入，结果是 token 数据，不会立即执行 call，也不会把这段代码直接注入正在编译的程序。

字符串插值默认生成字符串字面量，而不是将字符串内容当成代码。若需要将文本解析为表达式，使用 syn 的显式解析入口并处理错误；不能仅靠字符串拼接伪造作用域或受信任代码。

ToTokens 的调用仍是普通 goxide 方法调用，检查显式 impl、借用和 unsafe 属性。首版编译器不能为了取得 quote 结果而在编译期执行用户 ToTokens 或 AST 辅助函数；这样做就已经引入了延期的过程宏宿主。

Rust 的 quote! 自身采用声明宏形式，并通过 ToTokens 插值；这提供实现思路，不意味着 goxide 已具备它所需的全部基础能力。[quote! 文档](https://docs.rs/quote/latest/quote/macro.quote.html)

**完整 quote! 需要受控的前端基础能力。** 当前 token tree 捕获、token 字面量物化，以及 span / context 携带方式尚未冻结。可以先提供有限的 token 数据构造原语，再由额外 quote 包组合；不能宣称仅靠现有未完成的表达式捕获就能实现完整 quote。提供这些数据原语不需要开放任意编译期用户程序。

## 4. syn 的边界

syn 风格包解析 goxide 语法，不复用 Rust 的 AST 类型。可以共享 goxide 前端的词法和解析组件，但不直接公开编译器所有内部结构。

建议按普通能力拆分：表达式、类型、声明和文件解析；token 输出；只读遍历与显式重建。具体能力可按包或构建功能分离，不要求每个工具都携带完整编译器。

解析成功只说明语法可表示，不说明名字已绑定、类型正确、trait 已实现、match 穷尽、借用合法或 unsafe 已授权。修改 AST 后必须在真正编译时重新检查这些事实，不能把旧的语义结果复制到新节点上。

syn 不自行补充第三方 declare、查询全盘 impl 或取得额外私有访问能力。需要跨包类型分析的工具可以显式使用未来的语义查询 API；这一层不是普通语法解析器默认拥有的能力。

## 5. 源码位置、卫生与授权各自保留

共享语法协议必须分开三类信息：

| 信息 | 用途 | 不能替代的内容 |
| --- | --- | --- |
| span / 来源位置 | 诊断、导航、展示生成位置 | 不能仅因指向某处源码而得到其权限 |
| syntax context / 绑定身份 | 卫生、名字解析、定义点与调用点关系 | 不能由任意整数、字符串或文件路径伪造 |
| unsafe 授权来源 | 判断某个操作在哪个显式授权下出现 | 不能通过改 span、移动 AST 或序列化字段新增 |

公共 API 可以保留和转交已有片段携带的不透明上下文；不能提供随意构造 SymbolID、复制权限布尔值就变成受信节点的捷径。未来过程宏输出必须经过宿主校验，不能因为数据带了某个字段就视为编译器已经授权。

裸文本解析创建新的来源和未绑定名字，不从文本恢复已丢失的卫生身份。修改诊断 span 也不自动改变名字的解析上下文。模板和插值的上下文合成遵守[卫生宏规则](macros.md)，不能机械照搬另一个语言的默认 call-site 行为。

token 输出为文本会丢失某些绑定和来源信息；重新编译生成文件时按普通源码重新解析。这种工作流可以提供位置映射辅助诊断，但不承诺文本往返等价于卫生 AST 往返，更不能保留已经过期的借用或授权证明。

## 6. 与 Go 的双向互操作

这些包的普通数据和操作仍降低成 Go 的结构体、切片、接口和函数。Go 工具可以调用公开的解析、遍历和输出 API，构造或取得语法数据；库要对其公开输入进行必要的结构与版本验证。

Go 调用方不受 goxide 的源级检查，因此传回的数据不得直接携带可信编译器权限。来自 Go 的语法树、反序列化数据和缓存对象均需要按共享协议重新验证；单纯验过 Go 方法集不代表上下文真实。

Go 源码不能直接调用 goxide 的 `quote!` 语法，但可以调用普通 builder / parser API，或调用已由 goxide 展开的工具函数。不需要在 Go 程序运行时嵌入 goxide 宏解释器。

稳定公共 token / AST 协议与编译器私有的已解析 IR 分离。版本、节点种类、未知语法处理和来源表示需要显式协商；不能把不兼容版本的结构静默当成有效编译器输入。

## 7. 后续过程宏如何接入

过程宏阶段可以复用 syntax、syn、quote，但还必须另外定义：扩展依赖和加载、编译期执行环境、资源限制、输入输出协议、诊断、缓存失效，以及允许的宿主能力。不能把“能构造 token”当成已经完成这层设计。

未来宿主将输入 token 交给用户扩展，用户可用 syn 分析、quote 构造输出，再由宿主验证来源与类别，重新进入名字、类型和权限检查。用户程序能否读文件、哪些输入参与缓存等属于该阶段的独立决策，不因 Rust 允许某种能力就自动采用。

内建 Default / Clone / Debug 不需要等待此机制，它们由编译器登记的固定规则生成显式实现。用户可编程的 derive 才依赖过程宏扩展入口。普通 quote / syn 工具与这两种 derive 机制没有强制的启动依赖环。

## 8. 完成条件与顺序

以下顺序为暂定建议，完成条件供未来实现验收；不是已经确认的首版交付清单。

1. 先固定声明宏所需的 token tree、来源、卫生上下文与有限物化接口。
2. 提供可在普通工具中使用的语法协议、syn 解析 / 输出和 quote 构造能力；显式执行生成工具。
3. 验证语法往返、错误定位、片段来源、插值和重复；明确文本输出会丢失哪些信息。
4. 后续再提供过程宏宿主与自定义 derive，不让额外包隐式开启执行能力。

未来测试应覆盖普通工具运行与编译期执行的区分、字符串与代码插值的区别、未经授权的上下文伪造、跨版本数据、重复使用同一片段，以及生成代码重新接受完整前端检查。当前交付仅为设计，没有可运行的 goxide syntax / quote / syn 包。
